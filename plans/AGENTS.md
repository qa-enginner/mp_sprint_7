Этап 1: Анализ и подготовка контракта
Цель: Определить интерфейсы взаимодействия (API) между сервисами, опираясь на контракт из прошлого задания.

Review контракта (OpenAPI):

Убедитесь, что в контракте Auth-сервиса есть методы для валидации токенов (например, introspect), которые будут использовать Content Service и Admin Panel.

Добавьте эндпоинты для OAuth: /auth/oauth/{provider} (инициация) и /auth/oauth/callback/{provider} (коллбэк).

Добавьте эндпоинт для открепления соцсети: /user/social/{provider}/unlink.

Создание структуры проекта:

Организуйте код в соответствии с Clean Architecture

Выделите отдельные пакеты: auth, content, admin, oauth, middleware.

Этап 2: Интеграция с сервисами (Content & Admin) с учетом деградации
Цель: Обеспечить работу сервисов выдачи контента и админки при недоступности Auth-сервиса.

Разработка мидлварей (Middleware) в Content и Admin сервисах:

Кэширование валидации: При получении запроса с JWT/Access Token, сервис должен сначала проверить подпись токена локально (если используется JWT) или обратиться к Redis-кэшу, где хранится результат последней успешной валидации (статус, роли, user_id).

Circuit Breaker (Hystrix/Resilience4j/go-resiliency):

Оберните HTTP/gRPC клиент к Auth-сервису в Circuit Breaker.

Сценарий: Если Auth-сервис начинает отвечать ошибками (5xx) или таймаутами, Circuit Breaker переходит в состояние "Open". Запросы мгновенно отклоняются без попытки вызова Auth.

Fallback: При открытом состоянии или ошибке валидации:

Если токен локально валиден по подписи и не истек, но Auth не отвечает, считать пользователя аутентифицированным (но с пониженными привилегиями или пометкой "degraded mode").

Если токена нет или он невалиден, вернуть ошибку "Service Unavailable" (503) с заголовком Retry-After, но не "Forbidden", так как причина в инфраструктуре, а не в доступе.

Реализация механизма ограничения запросов (Rate Limiting) в Auth:

Выбор стратегии: Используйте Token Bucket или Leaky Bucket.

Хранилище: Redis (для распределенного лимитирования).

Ключи лимитирования:

По IP-адресу (client_ip).

По API Key (для сервисных аккаунтов Admin Panel — более высокий лимит).

По User ID для залогиненных пользователей.

Заголовки: Добавьте в ответы X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset.
